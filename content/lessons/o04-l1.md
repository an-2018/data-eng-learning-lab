# Optional data without losing people

## What you will be able to do

Retain every person while selecting only work-domain email values inside OPTIONAL.

## The problem

You are working with workforce and project data that will be used by another team. Your result must have a clear meaning, survive incomplete records, and be reproducible. This lesson focuses on **optional data without losing people** within sparql composition.

## Build the mental model

OPTIONAL extends existing mappings when a match exists and preserves them when no match exists. Put the required person pattern outside the optional group. Inspect unbound values explicitly rather than interpreting them as empty strings.

## Worked example

Read the example before running it. Identify the input facts or columns, the relationship being expressed, and the expected result.

```sparql
PREFIX ex: <https://example.org/>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
SELECT ?person ?email WHERE {
  ?person a ex:Person .
  OPTIONAL { ?person ex:email ?email }
}
```

## A mistake worth recognizing

> A FILTER on email outside OPTIONAL can remove people with no email.

Construct a small counterexample that would expose this mistake. Prefer three carefully chosen records to a large dataset whose behavior is hard to explain.
