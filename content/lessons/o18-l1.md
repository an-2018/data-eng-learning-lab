# Design named-graph boundaries

## What you will be able to do

Choose graph names and purposes for a publication pipeline.

## The problem

You are working with workforce and project data that will be used by another team. Your result must have a clear meaning, survive incomplete records, and be reproducible. This lesson focuses on **design named-graph boundaries** within dataset architecture, federation, and search.

## Build the mental model

Named graphs separate source snapshots, staging, quarantine, publication, and provenance. They do not by themselves provide access control, transactions, or truth claims.

## Worked example

Read the example before running it. Identify the input facts or columns, the relationship being expressed, and the expected result.

```sparql
PREFIX ex: <https://example.org/>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
SELECT ?person WHERE { GRAPH ex:snapshot { ?person ex:worksFor ex:northstar } }
```

## A mistake worth recognizing

> The default graph is not universally the union of every named graph.

Construct a small counterexample that would expose this mistake. Prefer three carefully chosen records to a large dataset whose behavior is hard to explain.

## Predict, then investigate

1. Choose graph names and purposes for a publication pipeline.
2. Identify what happens when a relevant value or relationship is missing.
3. Change one fact or row and predict which part of the result changes.
4. Explain the result using the vocabulary introduced above.
