# Updates and dataset state

## What you will be able to do

Show why running this migration twice does not create a second name assertion.

## The problem

You are working with workforce and project data that will be used by another team. Your result must have a clear meaning, survive incomplete records, and be reproducible. This lesson focuses on **updates and dataset state** within advanced sparql.

## Build the mental model

INSERT DATA adds explicit triples; DELETE/INSERT WHERE transforms matches. Design updates so retries produce the intended state. A sequence of HTTP requests is not automatically a transaction across all requests.

## Worked example

Read the example before running it. Identify the input facts or columns, the relationship being expressed, and the expected result.

```sparql
PREFIX ex: <https://example.org/>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
DELETE { ?p ex:oldName ?name }
INSERT { ?p ex:name ?name }
WHERE { ?p ex:oldName ?name }
```

## A mistake worth recognizing

> Generating new blank nodes on every retry can make a transformation non-idempotent.

Construct a small counterexample that would expose this mistake. Prefer three carefully chosen records to a large dataset whose behavior is hard to explain.

## Predict, then investigate

2. Identify what happens when a relevant value or relationship is missing.
3. Change one fact or row and predict which part of the result changes.
4. Explain the result using the vocabulary introduced above.
