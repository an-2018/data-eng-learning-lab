# Federate deliberately

## What you will be able to do

Decide when to query a remote source live and when to ingest a snapshot.

## The problem

You are working with workforce and project data that will be used by another team. Your result must have a clear meaning, survive incomplete records, and be reproducible. This lesson focuses on **federate deliberately** within dataset architecture, federation, and search.

## Build the mental model

Federated queries depend on remote services. Specify ownership, credentials, result limits, timeouts, retries, and fallback snapshots before adding a SERVICE dependency.

## Worked example

Read the example before running it. Identify the input facts or columns, the relationship being expressed, and the expected result.

```sparql
PREFIX ex: <https://example.org/>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
SELECT ?person WHERE { GRAPH ex:snapshot { ?person a ex:Person } }
```

## A mistake worth recognizing

> Federation does not make remote availability or statistics predictable.

Construct a small counterexample that would expose this mistake. Prefer three carefully chosen records to a large dataset whose behavior is hard to explain.

## Predict, then investigate

1. Decide when to query a remote source live and when to ingest a snapshot.
2. Identify what happens when a relevant value or relationship is missing.
3. Change one fact or row and predict which part of the result changes.
4. Explain the result using the vocabulary introduced above.
